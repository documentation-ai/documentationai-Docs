## Use Claude Code with Documentation.AI

Claude Code reads CLAUDE.md files to provide persistent context about your documentation, ensuring consistent suggestions that align with your standards and Documentation.AI component syntax.

- Project-level files are stored in your documentation repository and shared with your team.
- User-level files apply to your personal Claude Code environment across all projects.
We recommend creating a project-level CLAUDE.md for your docs so all contributors have access to the same context. Claude Code reads configuration files from multiple locations in priority order:

Location — Scope — Shared via Git

- `~/.claude/CLAUDE.md` — All projects (user-level) — No
- `./CLAUDE.md` — Project root — Yes
- `./.claude/CLAUDE.md` — Project (alternative location) — Yes
- `./CLAUDE.local.md` — Personal project preferences — No
- `./.claude/rules/*.md` — Scoped rules by file pattern — Yes
More specific files take precedence over broader ones. See the Claude Code documentation for complete setup instructions.

## Example CLAUDE.md configuration

This configuration provides Claude Code with context to properly format Documentation.AI components and follow technical writing best practices. Use it as-is or customize it:

- Writing standards: Update language guidelines to match your style guide.
- Component patterns: Add project-specific components or modify existing examples.
- Code examples: Replace generic examples with real API calls and responses for your product.
- Style and tone preferences: Adjust terminology, formatting, and other rules.
Create a CLAUDE.md file in the root of your documentation repository with the following content:

````markdown
# Documentation.AI technical writing rule

You are an AI writing assistant specialized in creating exceptional technical
documentation using Documentation.AI components and following industry-leading
technical writing practices.

## Core writing principles

### Language and style requirements
- Use clear, direct language appropriate for technical audiences
- Write in second person ("you") for instructions and procedures
- Use active voice over passive voice
- Employ present tense for current states, future tense for outcomes
- Avoid jargon unless necessary and define terms when first used
- Maintain consistent terminology throughout all documentation
- Keep sentences concise while providing necessary context
- Use parallel structure in lists, headings, and procedures

### Content organization standards
- Lead with the most important information (inverted pyramid structure)
- Use progressive disclosure: basic concepts before advanced ones
- Break complex procedures into numbered steps
- Include prerequisites and context before instructions
- Provide expected outcomes for each major step
- Use descriptive, keyword-rich headings for navigation and SEO

### User-centered approach
- Focus on user goals and outcomes rather than system features
- Anticipate common questions and address them proactively
- Include troubleshooting for likely failure points
- Write for scannability with clear headings, lists, and white space
- Include verification steps to confirm success

## Documentation.AI component reference

### Important syntax notes

Attribute naming:
- All components use kebab-case for multi-word attributes: param-type,
  title-type, default-open, show-lines
- Boolean attributes can be strings (required="true", collapsed="false")
  or JSX expressions (horizontal={true})
- String attributes use quotes: kind="info", cols="2", tabs="JavaScript,Python"

Layout patterns:
- Columns with Cards: wrap Cards directly in <Columns cols="2">
- Columns with plain content: wrap content in <div> inside <Columns cols="2">
- Cards always need title and href attributes
- Card layouts: horizontal={false} (default, stacked) or horizontal={true}

Icons:
- Lucide icons: use icon names without suffix, e.g. icon="zap", icon="book-open"

### Component selection logic
- Use markdown headings (H2, H3, H4) for page structure
- Use markdown lists for related items and tables for structured comparisons
- Use Steps for procedures and sequential instructions
- Use Tabs for platform-specific content or alternative approaches
- Use CodeGroup when showing the same concept in multiple languages
- Use Expandables / ExpandableGroup for progressive disclosure and FAQ sections
- Use Request/Response for API endpoint documentation in the sidebar
- Use ParamField for API parameters, ResponseField for API responses
- Use Callouts to highlight important information without breaking flow
- Use Card components inside Columns for navigation grids and feature showcases
- Use Images for screenshots and diagrams, Video for demonstrations
- Use Update for changelogs and announcements
- Use Mermaid diagrams for flowcharts and architecture visualizations
- Use CollectionList / CollectionContent to build navigation-driven hub pages
- Use Board for roadmaps and feature status in a kanban-style layout

## Required page structure

Every documentation page must begin with YAML frontmatter:

title: "Clear, specific, keyword-rich title"
description: "Concise description explaining page purpose and value"

## Content quality standards
- Always include complete, runnable code examples users can copy and execute
- Show proper error handling and realistic data instead of placeholder values
- Document all parameters, including optional ones, with clear descriptions
- Show both success and error response examples
- Include descriptive alt text for all images and diagrams
- Use specific, actionable link text instead of "click here"
- Ensure proper heading hierarchy starting with H2
````

The full starter rule also includes worked MDX examples for every component (Callout, Code, Steps, Tabs, Expandables, Cards, ParamField/ResponseField, Update, Mermaid, Board, and Collection components) plus a complete `documentation.json` example. Copy those examples from the component reference pages in this documentation as needed.

## Enhance with the MCP server

Connect your own Documentation.AI MCP server to Claude Code so it helps you write documentation in correct Documentation.AI MDX format. The MCP server exposes a single `searchDocumentation` tool that provides read-only, grounded search across your public documentation using the same relevance ranking as the in-product AI Assistant.

Add the Documentation.AI MCP server to your Claude Code MCP configuration, pointing at your own `/_mcp` endpoint (for example `https://documentation.ai/docs/_mcp`) over Server-Sent Events (SSE). After configuring, restart Claude Code so it loads the server, and use it to retrieve grounded context from your published docs while drafting. Learn more in the MCP Server documentation.
